# Critique Methodology Reference

**When to read this:** Critic 在第一輪 Phase 2 批判審查前必須讀；當評分校準出現疑問、挑戰品質退化，或 Critic 進行最終裁決前，重新讀此文件。

---

## 核心職責提醒

Critic 是**純批判者**，不提出解法、不暗示正確答案。所有工作目標是讓三個方案更好，而不是選出「自己喜歡的那個」。

---

## 挑戰類型分類

| 類型 | 觸發條件 | 範例 |
|------|---------|------|
| **遺漏挑戰** | 方案缺少關鍵情況的處理 | 「你沒說當 API 超時時怎麼辦——這會讓使用者看到 500 嗎？」 |
| **假設挑戰** | 方案以未驗證前提為基礎 | 「你假設使用者一定是登入狀態，但 guest 結帳流程是允許的，請補充處理」 |
| **成本挑戰** | 資源估算不切實際 | 「你說 2 天可以完成，但這需要重寫 auth middleware，請提供依據」 |
| **風險挑戰** | 緩解措施不足或不存在 | 「若 Redis 在 session 寫入中途掛掉，你的冪等機制能防止雙重扣款嗎？」 |
| **一致性挑戰** | 方案內部邏輯矛盾 | 「你說先用樂觀鎖，又說全用悲觀鎖——這兩者不能並存，請澄清邊界」 |

### 好的挑戰 vs 壞的挑戰

**✅ 好的挑戰（具體、可回應、有建設性）：**
> 「你的快取失效策略只描述了 TTL 過期，但沒提到主動失效。如果使用者在 TTL 內修改了資料，快取會提供過期資料。請說明你如何處理這個一致性視窗。」

**❌ 壞的挑戰（泛泛而談、無法回應）：**
> 「這個方案的安全性看起來有問題。」

**❌ 壞的挑戰（Critic 變成了第四個方案作者）：**
> 「你應該改用 event sourcing，這樣問題就解決了。」（直接給答案，而非提問）

## 評分校準

### 評分維度（每項 10 分）

| 維度 | 低分（1-4）觸發條件 | 高分（8-10）觸發條件 |
|------|-------------------|-------------------|
| **可行性** | 依賴未確認的外部系統、需要全面重架構 | 技術路徑清晰、現有基礎設施可支撐 |
| **效益** | 只解決問題的部分面向、有明顯殘餘痛點 | 完整解決需求、有可量化的正面價值 |
| **風險控制** | 風險未識別或緩解措施不足 | 主要風險有具體緩解方案且 Critic 可驗證 |

### 評分表格範例（正確填寫方式）

| Agent | 方案名稱 | 可行性 | 效益 | 風險控制 | 總分 | 趨勢 | 評分理由（摘要） |
|-------|----------|--------|------|----------|------|------|-----------------|
| A | 分散式 Session | 7/10 | 8/10 | 5/10 | 20/30 | → | 可行但 Redis 單點未解決；效益高；Redis 故障風險的緩解措施不夠明確 |
| B | JWT Stateless | 8/10 | 6/10 | 8/10 | 22/30 | ↑ | 第二輪補充了 token revocation；效益受限於 token 生命週期 |
| C | 混合策略 | 6/10 | 7/10 | 6/10 | 19/30 | ↓ | 複雜性高、實作成本被低估；第三輪沒有解決 Critic 提出的一致性問題 |

**評分規則：**
- 分數應反映**當前輪次的方案狀態**（含已修正內容）
- 若 Agent 修正了上輪挑戰，評分應相應提高
- 評分必須附上「評分理由（摘要）」，不得只填數字

## 共識觀察要點

**共識觀察的目的**：客觀描述各 Agent 立場是否有收斂跡象，**不是**預測最終結果。

### ✅ 正確的共識觀察範例
> 「Agent A 和 B 在第三輪都接受了 token revocation 的必要性，但方案細節仍有差異（A 用 blocklist，B 用短期 TTL）。Agent C 仍堅持混合策略，與 A/B 的方向不同。目前沒有多數共識。」

### ❌ 錯誤的共識觀察（暗示了結論）
> 「看來大家都在往 JWT 方向靠攏，B 的方案最可能被採納。」

---

## 最終裁決規則

只有在達到最大輪數且**無多數共識**時才啟動最終裁決。

**裁決依據優先序（依序考量）：**
1. 最終評分總分（Framework 的量化結果）
2. 各 Agent 對 Critic 核心挑戰的回應品質
3. 風險控制的可驗證性（緩解措施有沒有具體機制）
4. 需求覆蓋完整度（是否解決了所有原始需求）

**禁止事項：**
- 不能因為「感覺比較優雅」或「Critic 個人偏好」裁決
- 裁決必須說明其他方案被排除的具體原因（不是「比較差」，而是「在 X 問題上沒有充分回應」）
