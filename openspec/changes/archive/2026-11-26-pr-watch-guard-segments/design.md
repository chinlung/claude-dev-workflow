# Design: pr-watch-guard-segments

## 目的

pr-watch 的防護 hook（`plugins/pr-closeout/hooks/pr-watch-guard.sh`）原本拿整行命令判斷 `gh api` 是否為寫入：同一行任何位置的 `-X GET` 都替整行每個 `gh api` 的欄位解鎖。這次讓 GET 只替它自己的 `gh api` 解鎖。

威脅模型沿用 pr-watch：guard 是攔習慣性或誤跟文件而做的寫入的絆線，不是對付存心繞過的模型的邊界。模型會讀任何人寫的 PR 留言，所以要擋的是模型照著留言內容做出的寫入。

## 目標、非目標、反目標

- **目標**：欄位或 `--input` 只有在同一行每個 `gh api` 都有自己的 GET 時才放行；放行的集合是 1.2.0 放行集合的子集。
- **非目標**：
  - 不判斷一個旗標屬於哪個命令。別的命令的旗標（`… | cut -f1`、`rm -f`、`grep -F`、`bash -x`）仍會讓 `gh api` 被擋。
  - 不處理內容誤擋：heredoc、perl／node 程式本文、文件文字裡出現 `gh pr review`、`/replies`、`resolveReviewThread` 就擋。
  - curl／wget、`/replies`、`gh pr|issue comment|review`、GraphQL mutation 這幾條規則不改。
- **反目標**：
  - 任何一個 1.2.0 擋下、改完後放行的寫入。
  - 讓 hook 明顯變慢；它在監看期間對每個 Bash 呼叫都跑。

## 做法

寫入訊號（方法、欄位、`--input`）照舊在整行正規化後的 `$norm` 上讀。GET 的歸屬另外算：

1. 欄位或 `--input` 出現時，`$norm` 裡也 MUST 看得到一個 GET（所有方法旗標都是 GET），否則擋下。這是 1.2.0 的條件，原樣保留。
2. 再把命令做一次標記：轉小寫、先拿掉反斜線加換行（bash 也拿掉它），然後把分隔符（`|`、`;`、`&`、`(`、`)`、反引號、換行）、引號與反斜線，全部換成同一個標記字元 `$Q`，長度一對一。
3. 在標記後的字串裡逐個找 `gh api`（`$Q` 讀成空白，所以 `"gh" api` 找得到）。每找到一個，取它之後到第一個 `$Q`、再到第一個「空白＋`#`」為止的範圍，這個範圍裡 MUST 有 `-X GET` 或 `--method GET`，否則擋下。
4. `$norm` 找到幾個 `gh api`，標記字串也 MUST 找到至少那麼多個；少了就擋下。名稱被引號或反斜線拆開的 `gh api`（`"g"h api`、`g\h api`）只有 `$norm` 看得到，這一步讓它們不會溜走。

兩個視圖是「且」，不是「或」：步驟 1 是 1.2.0 的條件，原樣保留；步驟 3、4 只會再收窄它。所以不論標記視圖誤判什麼，放行的命令都是 1.2.0 放行的子集，誤判的方向只會是多擋。

### 邊界與錯誤處理

- 沒有 jq 時 `cmd` 是原始 JSON 文字，整段落在 JSON 的雙引號裡；結果只會多擋。沒有 jq 時 `deny` 本來就改用 exit 2。
- `tr` 與參數展開都以位元組處理；分隔符全是 ASCII，中文內容原樣通過。
- 每個 `gh api` 之後的範圍用「剩餘長度」切，而不是重新比對，所以標記字串與 `$Q`→空白的視圖長度必須一致；兩者都是一對一替換。

## 選過的做法

1. **寫入訊號也限在每個 `gh api` 所在的命令段**（原本的做法）。bash regex 逐塊掃描一條 4788 字元的命令要 15.7 秒；改用 awk 單趟掃描後速度可用，但連續三輪安全審查都找到繞法：引號內的 GET 被當成參數、`$( )` 與 `xargs` 帶進來的欄位落到別的段、`)` 關錯反引號那一層。根因是縮小寫入訊號的範圍，要求掃描器永遠不比 bash 早看到邊界，等於要一個忠實的 shell 解析器；另有 heredoc 本文含 `)`、`case x in a)`、brace expansion、`eval` 等同類形狀可預期。放棄。
2. **只縮小 GET 的範圍**（採用，使用者裁定）。縮小 GET 的範圍，誤判的後果永遠只是多擋，粗略的切法也安全。
3. **完全不做，只記成已知限制。** 誤放的前提在真實語料裡自然出現 11 次，不選。
4. **辨認命令位置**（只把位於命令位置的 `gh`、`curl` 當命令，引號與 heredoc 內的文字不判）。能同時解決內容誤擋，但要重新決定「直譯器字串內的寫入」（`node -e "fetch(…)"`）怎麼擋，是另一個設計，延後。

## 驗證證據

- 2564 條差分命令（手寫 1042、針對性探測、隨機 fuzz，另有 11 個 JSON 形狀）同時餵 1.2.0 與本版，並用會記錄參數的假 `gh` 實際執行：本版放行而 1.2.0 擋下的寫入，在補上「整行視圖也要看得到 GET」之後為 0。
- 317 條真實 `gh api` 命令重放：沒有任何一條從擋變放；3 條從放變擋，都是腳本本文裡一個沒有自己 GET 的 `gh api … -f`，原本靠同一行別處的 GET 過關。
- `tests/pr-watch-guard.test.sh`：24 個突變全部轉紅；突變打在 GET 的歸屬路徑上（分隔符與引號是否標記、範圍的終點、個數比對、續行處理、註解截斷、整行 GET 條件），不是它處理的資料。

## Trade-offs

這個設計接受下列已知的誤擋，方向都是多擋：

- 別的命令的旗標：`gh api … | cut -f1`、`rm -f`、`grep -F`、`bash -x`（語料 373 次呼叫中 1 次）。與內容誤擋同屬需要辨認命令位置才能解的那一類，已延後。
- 帶引號的端點寫在方法之前：`gh api "repos/…" -X GET -f per_page=100`，因為 GET 落在第一個引號之後。把 GET 移到端點前，或去掉引號即可。
- 反斜線續行把方法旗標本身拆開（`-\<換行>X GET`）：整行視圖看不到，所以擋下。
- 最壞情況的時間：語料中最長的命令在負載下約 1 到 2 秒（1.2.0 約 0.9 秒）。200 KB 的 `-f body=` 要 11.6 秒，超過 hook 的 10 秒逾時；逾時時 Claude Code 放行或擋下未查證，延後。

紅旗對照（`DESIGN-RED-FLAGS.md`）：

- **同一件事兩種做法（#6）**：命令有兩個視圖，`$norm` 整行與標記字串。兩者回答不同的問題（整行有沒有某個字；某個 GET 屬於誰），都在同一處、由同一個 `cmd` 產生，註解寫明各自給誰用。日後若辨認命令位置落地，整行規則改用它時要拿掉 `$norm`，不要並存第三種。
- **手動同步清單（#8）**：分隔符與引號集合在標記那一行只列一次。
