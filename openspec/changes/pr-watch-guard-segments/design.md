# Design: pr-watch-guard-segments

## 目的

pr-watch 的防護 hook（`plugins/pr-closeout/hooks/pr-watch-guard.sh`）現在拿整行命令判斷 `gh api` 是否為寫入，產生兩種錯：

- **誤放**：同一行另一個命令的 `-X GET` 會替某個 `gh api` 的欄位寫入解鎖。
- **誤擋**：別的命令的 `-f`、`-x`（例如 `cut -f1`、`bash -x`）被當成 `gh api` 的旗標。

這次只修 `gh api` 的方法、欄位與 `--input` 的判斷範圍（使用者裁定的選項 B）。其他規則照舊看整行。

## 目標、非目標、反目標

- **目標**：每個 `gh api` 只用自己那一段判斷。spec 的四個情境成立。
- **非目標**：
  - 內容誤擋不處理，例如 heredoc 或程式字串裡出現 `/replies`、`gh pr review` 這些字就擋。量測中這類佔多數（60 條非 curl 擋下中有 45 條），已進 follow-ups。
  - curl／wget、`/replies`、`gh pr|issue comment|review`、`resolveReviewThread` 等字、GraphQL mutation 這幾條規則不改。
- **反目標**：
  - 新增任何一種今天擋得下、改完後會放行的寫入寫法。
  - 讓 hook 明顯變慢。這個 hook 在監看期間每個 Bash 呼叫都會跑。

## 做法

### 一次掃描，標出引號

把命令（jq 還原、轉小寫）交給一支 `LC_ALL=C awk` 掃一遍，輸出一份「分段文字」。

- 不在引號內、也沒被反斜線跳脫的分隔符 `|`、`;`、`&`、`(`、`)`、反引號、換行，一律換成換行，所以一行就是一段。
- 在引號內或被跳脫的分隔符換成 `\x1f`（下稱 Q），段內仍看得到它原本是分隔的位置。
- 引號狀態有四種：無、單引號、雙引號、`$'…'`。
- 單引號內反斜線沒有作用。雙引號、`$'…'` 與無引號狀態下，反斜線跳脫下一個字元。
- 引號字元本身與反斜線不輸出，這和現有的整行正規化 `norm` 相同。字串內另一種引號字元也一併拿掉，所以 `sh -c 'gh api … "-f" …'` 內層的 `-f` 仍看得到。
- 分隔符清單只在 awk 裡寫一次，bash 端不再列一份。

### 每個 gh api 兩個範圍

bash 逐段讀，段內每遇到一個 `gh [旗標] api`，從它之後取兩個範圍：

| 範圍 | 終點 | 用途 |
|---|---|---|
| 寫入範圍 | 本段結尾（Q 視為空白） | 方法：任一個不是 GET 就擋；欄位或 `--input` 出現且沒有 GET 就擋 |
| 本身範圍 | 第一個 Q | 只有這裡的 `-X GET`／`--method GET` 算數 |

兩個範圍刻意不對稱。寫入訊號取寬，GET 取窄，引號解析出錯時偏向多擋。

- 引號內的 `|` 不切段，`--jq '.[] | .id' -f body=x` 的 `-f` 仍在寫入範圍內。
- 引號內另一個命令的 GET 落在 Q 之後，不算進本身範圍。例如 `sh -c 'gh api … -f body=x; gh api -X GET …'`。
- 一段裡有好幾個 `gh api` 時逐個判，任何一個擋就擋。

### 其他規則

- GraphQL mutation 規則照舊看整行：整行有 `gh api` 且有 `graphql` 與 `mutation` 就擋。
- `norm` 仍由原本的正規化產生，供其他規則使用。

### 邊界與錯誤處理

- **段落迴圈的寫法**：用 `while read … done <<< "$t"`，不用管線。這個迴圈跑在目前的 shell 裡，`deny` 的 `exit` 才有效。
- **引號沒閉合**：從那個引號到命令結尾全算在引號內，寫入範圍只會變大。bash 本身也不會執行這種命令。
- **沒有 jq**：`cmd` 是原始 JSON 文字。整段命令都落在 JSON 的雙引號裡，跳脫的引號不改變狀態，寫入範圍變大、本身範圍在第一個 Q 截止。結果是多擋。現行行為在沒有 jq 時本來就改用 exit 2。
- **非 ASCII**：轉小寫的 `tr` 與 awk 都以位元組處理。分隔符全是 ASCII，中文內容只會原樣通過。這呼應 CLAUDE.md 記下的 macOS awk 在 UTF-8 locale 下的中止問題。
- **awk 方言**：只用 POSIX awk 的 `substr`、`index`、`length` 與單字元 `RS`。macOS 的 BWK awk 和 CI ubuntu 的 mawk 都能跑。

## 選過的做法

1. **bash regex 逐塊掃描**：最初的原型。現有 87 條案例全綠，但一條 4788 字元的命令要 15.7 秒，舊版是 0.23 秒。雙引號那條含交替的 regex 在長字串上回溯，hook 不能用。
2. **awk 單趟掃描**（採用）：同一條命令 0.39 秒。整份語料 317 條最慢 0.8 秒，舊版同機約 0.25 秒級。
3. **perl**：寫起來最簡單，但 hook 會多一個執行依賴，awk 已經足夠。
4. **完整的命令位置解析**（選項 C）：能同時處理內容誤擋，但要重新決定「直譯器字串內的寫入」怎麼擋。使用者已裁定不在這次範圍。

## 驗證證據（原型，2026-11-26）

- 現有 `tests/pr-watch-guard.test.sh` 對原型 87 passed、0 failed（不含突變）。
- spec 四個情境，以及 `"$(… ; …)"`、`sh -c '… ; …'`、`$'\'|'`、跳脫分號 `\;`、`… | jq … | rm -f x; bash -x run.sh` 都判對。
- 語料 317 條整行重放，與舊版相比改變 3 條：
  - 1 條擋→放：`… | cut -f1`，這是要修的那一類。
  - 2 條放→擋：perl 本文裡沒有自己 GET 的 `gh api graphql -f`，舊版靠同一行別處的 `-X GET` 過關。這屬於內容誤擋的既有類別。

## 測試計畫

- **新案例**：spec 四個情境逐字入測。每個分支至少兩個觸發輸入：
  - 跨段 GET：`| cat;` 版本與 `&&` 版本。
  - 他段旗標：`cut -f1` 與 `rm -f`、`bash -x`。
  - 引號內管線：`--jq '…|…'` 與 `"$(…; …)"`。
  - 巢狀引號：`sh -c '…"-f"…'` 與 `bash -c "…'-f'…"`。
  - ANSI 引號：`$'\'|'`。
  - 跳脫分隔符：`\;` 與 `\|`。
- **突變打在掃描與範圍的執行路徑上**，每個都要讓指定案例轉紅：
  - awk 不辨認引號
  - 引號內分隔符不換成 Q
  - 本身範圍改用寫入範圍
  - 不拿掉另一種引號字元
  - 不處理 `$'`
  - 不處理反斜線
  - 段落迴圈改走管線（`deny` 不再生效）
- 舊有的 15 個突變中，`no-api-write` 與 `no-xanchor` 的取代式依附在被改寫的行上，要改成指向新的行，數量檢查同步更新。

## Open Questions
- [default] 掃描器用 awk，不用 perl：不新增執行依賴，速度已驗證。
- [default] GraphQL mutation 規則維持整行判斷：比逐段更嚴，改了只會放寬。
- [default] 語料重放的 2 條放→擋接受為正確行為，不另外處理：它們屬於已延後的內容誤擋類別。

## Trade-offs
- **紅旗 6「同一件事兩種做法」**：命令現在有兩種正規化，`norm` 給整行規則用，分段文字給 `gh api` 用。接受，因為兩者回答不同的問題，一個看整行有沒有某個字，一個看每段的旗標屬於誰。兩者在同一處、從同一個 `cmd` 產生，註解寫明各自給誰用。若之後選項 C 落地，整行規則改用分段文字時要把 `norm` 拿掉，不要並存第三種。
- **紅旗 8「手動同步清單」**：原型曾在 awk 與 bash 各列一份分隔符清單，已改成只在 awk 內一份。
